Technical Documentation

Mary — the WhatsApp AI brain

A self-hosted assistant that lives inside a WhatsApp conversation. The owner tags a message @mary; the brain reads the chat, reasons with Claude, runs real tools, and posts back — all as one enforced-JSON decision per turn.

@mary trigger LangGraph OSS FastAPI Claude Opus 4.8 Evolution API Postgres checkpointer Redis windows Google Calendar

Reflects the deployed system · prompt version 2026-08-03.1. Diagrams render on light cards for legibility in both themes.

Overview

The one-paragraph mental model, before any detail.

Mary sends and receives through one WhatsApp number — the owner's own. Because every message on that number is from the owner as far as WhatsApp is concerned, Mary can only be summoned deliberately: the owner writes @mary on a message. That opens a short listening window during which Mary reads every new message in the chat and decides, message by message, whether to speak, whether to run a tool, and whether to keep listening or close.

Each activation runs a small graph: normalise the message → decide if Mary should wake → gather the recent conversation → ask Claude for a structured decision → optionally run tools and feed the results back → post the reply. Everything Mary says is stamped with an assistant header so it is recognisable in the chat and so Mary never mistakes her own words for the owner's.

🧭

Two design seams keep it swappable. The graph depends only on a provider-neutral Reasoner interface (Claude sits behind it) and on a tool registry (backends plug in without touching the graph). Change the model or add a tool without rewiring the flow.

1Architecture & map

Where the pieces live and who talks to whom.

Everything runs on a single DigitalOcean droplet via docker compose. The Evolution API is the WhatsApp gateway; the Brain is our Python service (FastAPI + LangGraph). The Brain reaches out to two external clouds — Anthropic for reasoning and Google for calendar — and uses Postgres for durable memory and Redis for the listening-window markers.

2The listening window

How Mary is summoned, stays engaged, and steps back.

A window is a per-chat marker with a TTL (default 60s, key in Redis or in-memory). It is the difference between “Mary is engaged in this chat” and “Mary is dormant”.

  • Open — the owner (fromMe) sends a message carrying @mary. The window opens and the turn runs.
  • Continue — while the window is open, every new message in the chat (from the owner or the other participant) wakes the graph, so the owner can keep talking without re-tagging. Each successful reply refreshes the TTL.
  • Close — the model decides to end it (loop_state: "close_loop"), or the window simply lapses after the TTL of quiet. A time-lapse sends nothing.
🏷️

Tag matching has two guards. Tags are matched longest-first (so @assistente wins over @assist), and a tag only counts when the next character ends the word — @maryland does not trigger @mary.

Node by node, in common language

parseNormalise the incoming message

Takes the raw Evolution payload and pulls out the essentials: who the chat is, whether it came from the owner, the text, the message id, timestamp. It also works out two flags: is this one of Mary's own past replies (recognised by the header), and does the text start with a trigger tag?

Readsraw webhook body Writesremote_jid · from_me · text · msg_id · is_own · tag · trace_id Decidesnothing — pure extraction
gateShould Mary wake at all?

The doorman. Three outcomes: if the message is Mary's own echo → stop (never reply to yourself). If it is from the owner and carries @mary → open the window and run. If a window is already open for this chat → run (a continuation). Anything else → stop, silently, with a one-line “ignored” trace.

Readsis_own · from_me · tag + window state Writesdecision (run|stop) · trigger (tag|window) Routesstop → END · run → context
contextAssemble what Claude will read

On a chat's first activation it seeds the last 30 messages from Evolution; afterwards it fetches only what arrived after a stored cursor, so context is never re-loaded. Mary's own past messages are filtered out (they are already remembered as assistant turns). What remains becomes a single labeled transcript — “Marcelo: …”, “Contact: …” — and the cursor advances.

CallsEvolution findMessages (history) Writesmessages (+transcript) · last_whatsapp_message_id · context_message_ids · initialized
reasonAsk Claude for a structured decision

Builds the system prompt (owner identity, the “you are posting into a group chat” framing, the tool list, the JSON contract — shown in full in §6) and sends the transcript to the reasoner. Claude replies with enforced JSON: what to say, whether to keep listening or close, which tools to run now, and any in-flight workflow (goal + what's still missing). This node records the decision and all the metadata — it never posts a message itself.

CallsAnthropic messages.create (enforced JSON + web tools) Writesnext_message · loop_state · actions · workflow · lang · usage · … Routesactions? → execute · else → act
executeRun the tools, in order

For each action "domain.verb", dispatch to that tool's handler and append the result to the conversation as an observation Claude can read. Then the key routing decision: if any action was a read (a calendar list/search) or any failed, loop back to reason for a read-back (so Claude answers from real data, or recovers honestly). A clean write goes straight to act. Bounded by MAX_TOOL_ACTIONS = 4.

Callsthe tool handler (e.g. Google Calendar) Writesmessages (+observations) · action_results · _readback Routesread/fail → reason · clean → act
actSpeak and set the window

If there is a message, frame it with the localised header and send it via Evolution. Apply the loop decision: close_loop drops the window; otherwise refresh its TTL. Finally emit the one-row activation record (the audit line). This is the single place a sent message enters history — so every WhatsApp message is recorded exactly once, and silences never are.

CallsEvolution sendText Writesreply · sent · session_lang · messages (assistant turn) Routes→ END
⚖️

Execution ≠ closing. Running a tool does not end the window, and closing does not require a tool. They are two independent choices the model makes every turn. The TTL is the backstop that closes an abandoned window.

5JSON formats

Every payload that flows through a turn — what comes in, what Claude is required to return, and what we send back.

5.1 · Inbound — the Evolution webhook

Evolution POSTs a MESSAGES_UPSERT event. The Brain reads data.key, data.message, data.messageTimestamp, data.pushName. Text is drawn from conversation, or extendedTextMessage.text, or an image/video caption.

5.2 · History — normalised & the transcript

Each history row from findMessages is normalised, then the surviving rows become a single labeled transcript passed to Claude as one user turn. The speaker label comes from the header, not the message direction (everything is fromMe on a self-operated number).

5.3 · What the brain demands — the enforced schema

Every reasoning call constrains Claude's output to this JSON Schema (via output_config.format). The actions array is an anyOf of one branch per tool verb, each locking that verb's required inputs. Optional fields are simply omitted from required — never null-unioned — to stay under Anthropic's 16-union cap.

🛑

The 16-union cap. Anthropic structured outputs reject a schema with more than 16 anyOf/array parameters. Wrapping every optional field as anyOf:[T, null] pushed this to ~19 and silenced Mary in the first live test — every call returned 400. Optionals are now plain-typed & non-required (8 unions). A test guard asserts it stays ≤ 16.

5.4 · What Claude returns — examples

5.5 · Tool results — observation & ActionResult

The handler returns a structured ActionResult; execute turns each into a short observation appended to the conversation for the read-back.

🤥

No false “done”. A failed action returns { ok:false, error:… }, which forces a read-back — Mary reports the failure honestly rather than claiming success. She never confirms an action before seeing its real result.

5.6 · Outbound — sending & the audit line

Every turn also emits one activation record — the auditable summary of what happened.

6The system prompt

The exact instruction sent as the system parameter on every reasoning turn.

Assembled in app/prompt.py and frozen behind PROMPT_VERSION (currently 2026-08-03.1). Two parts are injected from a single source of truth, so the prompt can never drift from behaviour: the reply header text (from the same function that stamps outgoing messages) and the tool list (from the registry). The current date is refreshed each turn.

🧩

Why it says “his WhatsApp”. Mary operates the owner's own number, so the prompt is explicit that replies are public to the whole chat and that only the owner's messages are commands — a deliberate guard against a group participant instructing Mary. The header is described here, never written by the model; act stamps it.

7State & memory

What persists across turns, and what is scratch for a single turn.

The graph carries one MessageState. A slice of it is persisted per chat by the checkpointer (keyed by a stable thread id, sha256(instance : chat_jid)); the rest is per-turn scratch. Conversation history uses LangGraph's add_messages reducer, and the ingestion cursor guarantees each WhatsApp message is folded in exactly once.

🧠

Memory bootstrap. First activation seeds the last 30 messages from Evolution and saves the cursor. Later activations load the checkpoint and fetch only messages after the cursor — context is assembled once, then extended, never reloaded.

8The tool model

One registry, fanned out into every seam.

Tools are declared once in a registry. Each is either local — run inside the execute node, contributing its input schema to the enforced JSON — or anthropic_mcp — a remote server Claude calls inline via the connector (wired, none registered yet). At startup the registry fans out into four things: the output schema (local), the MCP server config (mcp), the prompt's tool list (both), and the handler instances (local). Add a tool to the registry and every seam updates.

Calendar verbs (local · Google Calendar)

calendar.createtitle, startend, duration_min, virtual, location, attendees, send_invites45-min default; location XOR virtual (video wins → Meet); invites emailed unless disabled.

🔎

Search-first for edits. To change or cancel, the model must first calendar.list to resolve the event_id, match it, and confirm — it never invents an id. The schema enforces this: update/delete require an event_id, and only a list produces one.

10Logging & tracing

How every activation is recorded — two levels under one trace id.

A trace id is minted in parse — mary-⟨chat⟩-⟨ms⟩-⟨rand⟩ — and everything about that run is logged under it, at two levels that share the id, so a run can be replayed from either angle:

  • Code level — the builder's view: one structured event per node with its decision variables, the provider/tool calls (arguments and replies), and timings. The debugging stream.
  • User level — the human transcript: what the owner sent vs. what Mary posted back.

A gated-out message writes just a one-line “ignored” code event, keeping the stream clean. Only messages Mary actually spoke are stored as assistant turns in memory — silences never are.

11Guarantees

The correctness rails that keep a self-operated number safe.

🔁 No echo loops

Every reply carries an assistant header; incoming messages that match a header (in any supported language, plus retired ones) are recognised as Mary's own and never re-processed.

🎯 Idempotency

Webhook retries are dropped by a bounded LRU of seen message ids, so the same message never runs twice.

🔒 No races

A per-chat lock serialises activations, so two fast messages in one chat can't corrupt the checkpoint or the window.

🤐 Safe silence

Any provider error, refusal, or unparseable output falls back to “stay silent, keep listening” — a failure never posts garbage into the chat.

✅ Honest results

Success is only claimed after the real tool result is read back. Failures are reported, not hidden.

🧪 Schema guard

A test asserts the enforced schema stays under the 16-union cap, so the outage that silenced Mary can't silently return.
