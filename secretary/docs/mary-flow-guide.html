Drift & honesty

Overview — one message through the whole flow

A message from the owner's WhatsApp lands on the Evolution webhook. If it summons the secretary (the @mary tag) or continues a live conversation, it runs the orchestrator turn loop: the model makes ONE decision per turn — keep listening, run a skill, answer directly, or close — bounded by hard caps in code. Six of seven skills make zero Claude calls; the router's single merged classify-and-extract call does all the extraction.

0 · Webhook intake & fast-ACK

Where a message enters. The webhook acknowledges before it does any work, and drops duplicates.

railsread
inside
  • app.post("/webhook") receives the Evolution payload and immediately calls res.sendStatus(200) — before any routing — so Evolution never resends the same message while a turn is running.
  • Dedup by messageId: a seen Set holds the last 500 ids; a repeat id returns early.
unhappy · dedup drop: if (id && seen.has(id)) return; — an id already in seen is a resend and is dropped silently.

Provenance: server.js:332, server.js:333, server.js:386.

1 · Buffer & extract

Every inbound message is remembered for context — even the ones that do not summon the secretary.

railsread
inside
  • remember(remoteJid, {…}) buffers EVERY message with text, so the transcript the router later sees carries the whole conversation, not just tagged lines.
  • extractText(data.message) pulls the text; getQuoted(data) returns { id, hasAudio, mediaType, text, calendarLink } for the replied-to message; inboundMedia(data, quoted) lists attachments (attachment first, then quote).
  • A captioned document has text === "", so its tag+order ride on the attachment caption, computed at attachmentCaption.

Provenance: server.js:338, server.js:342, server.js:348, and the extractors in lib/whatsapp.js.

2 · The @ trigger gate

Decides whether this message is for the secretary at all: START a flow, CONTINUE an open one, or IGNORE.

railsread
the three doors
  • START: the owner (fromMe) used a trigger tag — matchedTagNew(gateText) returns the matched tag (longest-first, must end at a word boundary). Its length is sliced off to form the order.
  • CONTINUE: a session is open and this message comes from the awaited party — session.awaitFrom is owner / contact / any. No tag or reply required.
  • self-guard: isOwnMessage(text) — the secretary shares the owner's WhatsApp account, so its own replies arrive with fromMe=true; the header check is the only thing telling them apart.
unhappy · IGNORE: if (!isTagged && !isContinuation) return; — not tagged and no session waiting on this sender → the message is buffered (node 1) but no turn runs.

Provenance: server.js:357, server.js:367, server.js:385, server.js:399, and lib/identity.js:152.

3 · Context build — ctx

The rails' public API to the skills: one object carrying the conversation, the send helpers, and the language pin.

railsread
inside
  • fetchHistory → combine → buildTranscript (the ME:/OTHER: string the six unconverted skills read) and buildLabeledTranscript (the OWNER/SECRETARY/CONTACT view the model reads).
  • ctx.send — an ordinary reply, never scanned; it records the body onto ctx._turn.said for the read-back. ctx.sendFailure — a declared soft failure; it fires a self-learning report. ctx.dmOwner — an additive private note to the owner's own number (no-op if unset).
  • language pin: pinnedLang = session?.openingLang; each turn's language is resolveTurnLang(pinnedLang, reply.lang) — an ongoing conversation HOLDS its opening language.

Provenance: server.js:414, server.js:421, server.js:467, server.js:509, and the pin policy in lib/lang.js:20.

4 · Media prep

Relays inbound images/PDFs to the turn call as Anthropic multimodal blocks — with size caps and a spoken notice for every reason a file cannot be read.

railsreadcaps
caps
  • IMAGE_MAX_BYTES = 5 MB  ·  PDF_MAX_BYTES = 32 MB  ·  MAX_FILES_PER_TURN = 10.
  • Download with getMediaBase64, check bytes against the per-type cap, build the block with mediaBlockFor (validated against an allow-list — a leaked audio/ogg default can never become an image block).
  • History fallback: an @mary turn with no attachment whose words mention a file (mentionsFile(order)) reaches back for the most-recent relayable file via historyMediaFile.
unhappy · per-reason notices: fileTooMany (>10), fileDownloadFailed, fileTooLarge, fileUnsupported — one note per distinct reason; if nothing readable remains, the notes are sent and the turn closes without routing.

Provenance: server.js:79, server.js:80, server.js:621, server.js:633, server.js:641.

5 · Marker & turn-loop bounds

A model that can call skills in a loop can loop on skills — so the bound is code, never the model. The marker carries the counters across message boundaries.

railscaps
the bounds
  • MAX_TURNS = 10 (counts only PRODUCTIVE turns — deliberate silence is free), MAX_DISPATCHES = 3 (a dispatch may be a read, not only a write), MAX_REPAIRS = 2, READBACK_CAP = 8192 bytes, MARKER_TTL = 15 min, NATIVE_MAX_ANSWERS = 6.
  • persistMarker / closeMarker both refuse to touch the key when a dispatched skill has taken it (its skill field) — a skill's pending confirmation outranks the orchestrator marker.
cap · turn cap trip: if (marker.turns > MAX_TURNS) → the deterministic turnCap apology, close, and a report.

Provenance: server.js:294, server.js:295, server.js:305, server.js:565, server.js:709.

6 · The router call — route() ★

The heart. ONE Claude call classifies intent AND extracts the first skill's declared inputs in the same breath — one round-trip, not two.

railsprompt #1–#4
inside
  • route(ctx, turn) builds the system prompt from buildRouterSystem(owner, catalog, tags) and one of three user prompts (first-turn / read-back / repair), then makes a single messages.create with max_tokens: 1024 and no output_config (deliberate — see the prompt file; it keeps the orchestrator schema-free).
  • The reply is logged as ROUTER RAW: … and parsed by parseJsonReply, a balanced-brace scanner that is load-bearing (~4% of replies leak a line of prose before the JSON).
  • Returns { say, next, skills, info, lang, awaitFrom, degraded }. next ∈ listen | execute | done | answer.
unhappy · degrade: a refusal or unparseable reply returns { next:"done", skills:[], degraded:true } — the schema-drift alarm that server.js turns into the "didn't understand" menu + an unrouted report.

Provenance: router/router.js:85, router/router.js:155, router/router.js:32, router/router.js:177, and the system prompt router/prompt.js:28.

7 · Branch on next

The turn-loop switch. Four outcomes, inline in the webhook handler.

rails
  • listen — send say (if any), record awaitFrom, persist the marker, and wait for the next message. A {say:null, next:"listen"} silence is FREE (does not consume a turn).
  • answer — the tool-carrying answer pass (node 7a).
  • done — close. A degraded done fires the "didn't understand" menu + unrouted capture; a legitimate empty done closes silently.
  • execute — dispatch (node 8). Forbidden on a read-back turn (the write invariant).

Provenance: server.js:716, server.js:728, server.js:765, server.js:784.

7a · Answer pass — answer()

A SECOND, tool-carrying prose call — distinct from the JSON router call. Because it is downstream of a parsed classification, it can never reach the "didn't understand" menu.

railsprompt #5–#6caps
  • Attaches the native toolset from buildNativeTools(env) — web search + web fetch (code execution gated off) — and asks for PROSE, delivered inline in the same WhatsApp reply.
  • Server-side tools run an internal loop; a pause_turn stop is resumed by resending [user, assistant(content)], bounded by NATIVE_MAX_TOOL_HOPS_DEFAULT = 4 and each call by NATIVE_ANSWER_TIMEOUT_MS = 30s.
  • Outcome ∈ ok | timeout | tool_error | empty | refusal. A per-conversation ceiling NATIVE_MAX_ANSWERS = 6 is enforced on the marker.
cap · still paused after the hop cap → treated as a timeout (bounded, never runs away). A refusal stays silent.

Provenance: router/router.js:243, router/router.js:273, router/router.js:280, lib/nativeTools.js:37, and the marker ceiling at server.js:737.

8 · Dispatch & payload validation

The router's info is never trusted. Plain code — no AI — decides whether the payload is usable before any skill sees it.

railscaps
the three tiers & two gates
  • checkPayload(inputs, info) returns { shapeOk, ok, problems }: shapeOk = validity only (right fields, right types, no extras); ok = validity + completeness + the skill's own consistency predicates.
  • orchestrator tier gates on ok — a failure is the REPAIR loop, not a dispatch: describeProblems(problems) goes back to the model (ORCHESTRATOR repair: … is logged), the write budget untouched.
  • skill tier gates on shapeOk — shape-valid is handed over (incomplete or not); shape-invalid is withheld (ROUTER payload withheld: …) and the skill re-extracts for itself.
cap · dispatch ceiling (MAX_DISPATCHES) and repair give-up (MAX_REPAIRS) each end the turn with a deterministic apology + report. A batch is deduped, order preserved.

Provenance: lib/inputs.js:212, lib/inputs.js:271, server.js:831, server.js:841, server.js:793.

9 · Skill run (pure task)

The chosen skill runs. Six of seven make zero Claude calls — the router already extracted their inputs. Only the primary's return value drives a read-back.

rails
  • The dispatch loop runs each task's run(ctx). ctx.info carries the pre-extracted payload to the ONE task it belongs to; every other skill sees null and extracts for itself.
  • ctx._turn.skill is set so a soft report names the skill; ctx.session is nulled so a dispatched skill never receives the orchestrator's marker.
  • A non-primary converted skill cannot batch — it is skipped with a dispatchSkipped notice. Per-skill internals are in the Skills section.

Provenance: server.js:854, server.js:867, server.js:871.

10 · Read-back turn

After a converted skill returns a value, the model gets one more turn to narrate the result — but it may NOT act again.

railsprompt #3cap
  • The return value is serialized and truncated at READBACK_CAP (8192 bytes, then …[truncated]), then fed to buildReadbackUser which reuses the router SYSTEM prompt.
  • Write invariant: a read-back turn may not execute and may not start a fresh answer pass — a new action needs a new message from the owner first. Both are refused with a report.

Provenance: server.js:786, server.js:893, server.js:903, and the prompt router/prompt.js:179.

11 · Reply to WhatsApp

The send boundary: translate if needed, frame with the bold header + italic body, and hand to Evolution.

rails
  • localizeBody is the long-tail translation fallback: en/pt pass through unchanged; any other pinned language is translated by a cheap model (with a no-op guard against "translate X→X"). Markers are added AFTER translation so the model never sees them.
  • send() calls frame(headerFor(lang), body) — frame italicizes line-by-line (URLs and marker-bearing lines stay plain) and stamps the language-aware header — then evolution.sendText.
  • A model-authored say in the other maintained language is force-translated first (shouldForceTranslateSay).

Provenance: server.js:170, server.js:198, lib/format.js:48, lib/identity.js:84, lib/lang.js:38.

Infra · Confirmation (confirm-first writes)

The guardrail on every calendar/task WRITE. Before anything is written to the world, the owner must have agreed.

railsprompt #10write-gate
  • classifyConfirmation(ctx, {action, who}) classifies the latest message as confirm / decline / unrelated. unrelated is the SAFE default: any doubt, refusal or API error lands there, so an unclear message can never trigger an irreversible write.
  • buildConfirmSystem(action) puts a short English description of what is pending into the prompt so a "yes" is unambiguous.

Provenance: lib/confirm.js:33, lib/confirm.js:53, lib/confirm.js:56.

Infra · The declared-inputs contract

How the router asks for a skill's inputs without the orchestrator ever importing that skill's schema.

rails
  • describeInputs(catalog) renders each skill's manifest.inputs as OPAQUE prompt text (the skill menu + each skill's rulebook, incl. the calendar rulebook — prompt #7).
  • checkPayload validates whatever came back against that declaration; describeProblems renders failures into the repair prose. It names a field of no skill.

Provenance: lib/inputs.js:124, lib/inputs.js:212, lib/inputs.js:271.

Infra · Self-learning capture

A malfunction is exactly three things: a thrown code error, a declared soft failure (ctx.sendFailure), or the owner reporting a defect (the feedback skill). Each writes one Markdown report.

railsprompt #11
  • captureFailure(ctx, info) renders a report (render()) carrying the order, transcript, and the recent redacted ring lines. It is the source of every worked trace below.
  • analyze() (prompt #11) appends a best-effort "likely cause" hunch — its own try/catch, returns null on any error. Marked UNVERIFIED in every report; not a main-path call.

Provenance: lib/selflearning.js:248, lib/selflearning.js:132, lib/selflearning.js:180.

Infra · The log ring (redact + truncate)

An in-memory ring so the secretary can read its own recent logs back into a report — with secrets masked and long lines cut BEFORE they enter.

rails
  • CAPACITY = 500 entries, MAX_LINE_CHARS = 2000 — the long TRANSCRIPT>>> line is cut with a «truncated N chars» marker.
  • redact() masks keys/tokens/high-entropy blobs → «redacted:anthropic-key», «redacted:google-key», «redacted:blob», … These tokens ride VERBATIM into every trace below; they are never un-redacted.

Provenance: lib/logbuffer.js:18, lib/logbuffer.js:40, lib/logbuffer.js:62.

Infra · Native tools

The server-side tool bundle attached to the answer pass. Config-driven; disabled degrades safely to a tool-less answer.

rails

Infra · Language (pin / hold)

The rails decide and carry the conversation language; each skill only supplies its own {en,pt} strings.

rails

  • resolveTurnLang(pinnedLang, routerLang) — an ongoing conversation HOLDS its opening language; only a new conversation's first turn adopts the router's detected lang. translationNeeded is the no-op guard.

Infra · Format & Identity

How a secretary message looks, and how it is told apart from the owner's own typing.

rails

  • headerFor(lang) stamps the language-aware header; isOwnMessage recognizes every header variant (both languages + retired ones) so the bot never reads its own reply; matchedTagNew matches trigger tags longest-first.

#1 · Router SYSTEM — buildRouterSystem(ownerName, catalog, tags)

The router "prompt" is a template PLUS the runtime-assembled catalog: describeInputs(catalog) concatenates each skill's declared inputs AND each skill's own rulebook (including #7). It is not one flat string.

▶ template (interpolation points: ${ownerName}, ${tasks}, ${tags}, ${rulebooks}) 
You are ${ownerName}'s secretary, and you HOLD THE CONVERSATION with him. On every
incoming message you make ONE decision: keep talking, run a skill, or close …

You do THREE things in one pass:
(1) decide the next state — LISTEN, EXECUTE or DONE;
(2) when you EXECUTE, pick the skill(s) and EXTRACT the first skill's declared inputs;
(3) detect the conversation LANGUAGE.

Available tasks:
${tasks}                 <-- describeInputs(catalog): the skill menu + each skill's INPUTS

## THE FOUR STATES — "next"
- "listen"  = send me the next message. The conversation stays open …
- "execute" = run a skill now. Put the skill id(s) in "skills" and the first skill's inputs in "info".
- "answer"  = a direct QUESTION best answered by you (native web tools) …
- "done"    = this conversation is over …

## YOUR REPLY FORMAT — READ THIS CAREFULLY
Reply with a SINGLE JSON object and NOTHING else:
{"say": "<prose>" | null, "next": "listen"|"execute"|"done"|"answer",
 "skills": ["<id>", ...], "info": { ... }, "lang": "<iso639-1>",
 "awaitFrom": "owner"|"contact"|"any"}

## YOUR TRIGGER TAGS (your own state)
TAGS: ${tags}

${rulebooks}             <-- each skill's EXTRACTION RULES, verbatim (incl. the calendar rulebook, #7)
▶ rendered example (ownerName="Marcelo", tags="@mary, @assistente")

#5 · Answer-pass SYSTEM — buildAnswerSystem(ownerName, lang)

▶ template

Drift & honesty

This is a hand-authored snapshot; it rots as the code changes. Mitigations baked in: a file:line citation on every block, prompt and hop, and the build-time commit stamp at the top (aca9c96). A maintainer who suspects drift can jump straight to the cited source.

Two honesty rules govern the traces, and both are load-bearing:

  • Two hops are NEVER logged — the skill's successful RESULT object and the framed reply actually SENT to WhatsApp. Both are always labelled reconstructed, rebuilt from the skill's own skill.js return shape and from frame(). Two skills DO log on success, but only a status string / a length (7. Assistant Settings/skill.js:93, 4. Feature Requests/skill.js:192), never the return object.
  • Redaction and truncation are preserved verbatim. A «redacted:…» secret or a «truncated N chars» cut is never "completed" to make a trace look whole (lib/logbuffer.js:40). Reports are also partial — the ring holds 500 entries and cuts lines at 2000 chars — so a missing hop is shown as a gap, never invented.

Router-shape drift is its own axis: older captures carry the pre-merge {tasks,lang,info} shape and newer ones the merged {say,next,skills,info,lang,awaitFrom} shape. Both appear on disk, so every trace stamps its own capture date + shape above.
