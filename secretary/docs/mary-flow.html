The @mary flow

Everything that happens from the moment a WhatsApp message carrying the @mary tag is read — what triggers, what prompts and context are passed, what each step expects back, and every place it can fail. Traced from the live code in secretary/1. Orchestrator/ and secretary/3. Mary Skills/.

🧭 The one idea that explains everything
The skills are pure tasks. They hold no conversation, no session dialogue, and (for the seven @mary skills) make no LLM call of their own. The orchestrator's model runs the entire dialogue — clarifying, proposing, confirming — over listen turns, and dispatches a skill only once it has a validated payload. A skill's run(ctx) reads ctx.info, acts, sends one message, and returns a JSON value that drives one final "read-back" turn. So the "prompts" you're looking for are the router system prompt plus each skill's rulebook() and field descriptions, merged into a single router+extractor call — not per-skill templates.

Overview & architecture

The whole flow — intake, gate, context build, media prep, and the multi-turn loop — runs inside a single POST /webhook request handler (server.js:332–911). Only counters cross message boundaries, persisted on a Redis "marker". The pipeline:

The router returns one of four states each turn — listen (reply and wait), execute (run skill(s)), answer (native web/tools answer), done (close) — and the loop iterates until a terminal state or a cap.

Stage 0Webhook intake & fast-ACK

Trigger any HTTP POST /webhook from Evolution (server.js:332).

The handler ACKs before any work so Evolution never resends. The whole body is inside one try whose only catch is a last-resort console.error (server.js:908–910) — any unhandled throw is swallowed and the user gets nothing.

app.post("/webhook", async (req, res) => {
  res.sendStatus(200);              // reply fast so Evolution does not resend
  const data = req.body?.data;
  if (!data?.key) return;           // silent drop
  const { fromMe, remoteJid, id } = data.key;
  const text = extractText(data.message).trim();
⚠ Gotcha
extractText (whatsapp.js:9-18) reads conversation / extendedTextMessage.text / image & video captions — there is no documentMessage branch, so a captioned PDF yields text="". That's why the gate falls back to the attachment caption.

Stage 1The @ trigger gate — start / continue / ignore

Three exact conditions decide whether a message is even looked at.

1a · Own-message filter

The secretary's own replies come back with fromMe=true (owner and bot share one account), so the discriminator is a header check: isOwnMessage(text) (identity.js:108-111) matches the reply header ([…'s AI Assistant]:, [Assistente IA de …]:, plus legacy headers in ALL_HEADERS).

1b · START — the @mary tag (owner only)

const gateText = text || attachmentCaption;
const tag = fromMe ? matchedTagNew(gateText) : null;   // fromMe is a HARD precondition
const isTagged = !!tag;
  • fromMe is required — a non-owner message can never open the gate.
  • matchedTagNew (identity.js:152-159) matches NEW_TAGS longest-first, requiring a word boundary after the tag.
  • NEW_TAGS is seeded from SECRETARY_TAG_NEW (default @mary); a stored Redis value from the assistant_settings skill overrides it at boot.

1c · CONTINUE — untagged follow-up while a session is open

A continuation needs an open session, no tag, not the bot's own message, and the sender to match session.awaitFrom (owner→fromMe, contact→!fromMe, any→either) — server.js:375-382. This is what lets the other party answer during a booking.

1d · IGNORE + dedup

if (!isTagged && !isContinuation) return;      // silent drop
if (id && seen.has(id)) return;                 // in-memory dedup (Set of 500)
⚠ Failure surface
Both the seen dedup and the session store's in-memory fallback are lost on restart. If Redis is down, sessions.get falls back to an in-memory Map (sessions.js:63-73) — so across a restart or a second replica, open sessions vanish and every continuation silently becomes an ignored message.

The labelled transcript (three speakers OWNER/SECRETARY/CONTACT) is built once (server.js:542) and passed into every router turn. nowStr is hard-pinned to America/Sao_Paulo.

Stage 3Media prep (before the loop)

Runs once; result on ctx.media (null keeps text turns byte-identical). Per-file download → validate → allow-list. Caps: MAX_FILES_PER_TURN=10, image ≤ 5 MB, PDF ≤ 32 MB. Only image/jpeg|png|gif|webp and application/pdf are relayed; anything else (incl. the audio/ogg default) is dropped as fileUnsupported (whatsapp.js:210-225).

  • If the turn carries no files but the order mentions one, a 1-hour history fallback pulls the most recent image/PDF (server.js:599-603).
  • File turns are pinned to VISION_MODEL (default claude-sonnet-5), independent of CLAUDE_MODEL, so the model choice can't disable vision/PDF.
  • If nothing readable survives → notices sent, marker closed, turn ends without routing.

Stage 4The turn loop

An unbounded for (turnIndex=0; ; turnIndex++) (server.js:668-907); every exit is a return or a cap. Each iteration calls route(ctx, turnArg) and acts on reply.next:

nextWhat happensEnds turn?
listensend say (if any), set awaitFrom, persist marker, wait for next messageyes
executevalidate payload → dispatch skill(s) → collect result → loop into a read-back turnno (loops)
answerrun answer() native-tool pass, send prose, stay openyes
doneclose; if degraded on turn 0 → the "I didn't understand" skill menuyes

Key loop rules:

  • Productive-turn cap: MAX_TURNS=10; a deliberate-silence turn ({say:null,next:"listen"}) is free.
  • Dispatch cap: MAX_DISPATCHES=3 (a dispatch may be a read).
  • Payload gate: an orchestrator-conversation skill gates on full validity (ok); a failure enters the repair loop — the model gets describeProblems() back and re-emits, giving up after MAX_REPAIRS=2 with repairGiveUp.
  • Write invariant: a read-back turn may not execute or answer — attempts are refused silently and captured (readback_execute/readback_answer).

Stage 5The skill contract

Each skill exports { manifest, run }. manifest = { id, description, inputs?, conversation? }. run(ctx):

  • reads ctx.info (the router-extracted, pre-validated payload) and other ctx fields;
  • sends exactly one outcome via ctx.send (guidance) or ctx.sendFailure (a real malfunction → files a report);
  • returns a JSON-serializable value — undefined ends the cycle; anything else is serialized (truncated to READBACK_CAP=8192 bytes) and fed into one read-back turn.

Stage 6Read-back & the reply to WhatsApp

The serialized return + the prose the skill already sent (_turn.said) are handed to the model in a read-back turn so it can narrate the outcome or chain a follow-up (it may not act again). Every outbound message goes through send() (server.js:198-201): localizeBody (translate for non-en/pt via TRANSLATE_MODEL; on error returns the source text) → frame(header, body) → evolution.sendText.

⚠ The most invisible failure of all
evolution.sendText on a non-OK response only logs and returns false — it never throws (evolution.js:14-22). So a failed WhatsApp delivery is invisible to the loop: the code believes it replied, and the user simply gets nothing. This is the single most likely "it just didn't answer" cause that leaves no user-facing trace.

## THE FOUR STATES — "next"
- "listen"  = send me the next message. The conversation stays open. Use this to ASK a question,
              to PROPOSE something and wait for his agreement, OR to stay silent on chatter that
              is not for you (say:null). While you listen you also declare WHO you wait on next
              (see "awaitFrom").
- "execute" = run a skill now. Put the skill id(s) in "skills" and the first skill's inputs in
              "info". Executing IS acting — do it only when you should act.
- "answer"  = this turn is a direct QUESTION best answered by you, using the live web, a URL
              already in the thread, real computation, or general knowledge that NONE of the
              skills above cover. Return next="answer" with NO "skills" and NO "info"; I will
              research and answer him inline in the same reply. Use this ONLY for a genuine
              question to answer — never for anything one of the skills above already owns, and
              never as a way to "just reply" (that is say=prose with next="listen").
- "done"    = this conversation is over. Use it ONLY when Marcelo has clearly finished —
              he said thanks/bye/"that's all", explicitly ended it, or told you to forget it —
              OR the exchange has genuinely wrapped with nothing left pending.

## STRONGLY PREFER "listen" — DO NOT CLOSE EARLY
Your default bias is to STAY OPEN. After you act or answer, keep the conversation open with
next="listen" and wait for his next message. Answering ONE thing is NOT a reason to close — he
almost always has more to say, and if you close he cannot reach you: his next message is dropped
because nothing is open. So:
- If he has signalled an ongoing task ("I have a job for you", "hang on", "one sec", "let me
  think") — stay "listen". The job is not over just because you replied once.
- If it is plausible that more is coming — stay "listen".
- Only emit "done" when he has clearly wrapped up (above). When in doubt, "listen", never "done".

## YOUR REPLY FORMAT — READ THIS CAREFULLY
Reply with a SINGLE JSON object and NOTHING else. No prose. No explanation. No markdown
fences. No text before or after. Your entire reply must be exactly one JSON object:

{"say": "<prose to him>" | null, "next": "listen" | "execute" | "done" | "answer", "skills": ["<skill id>", ...], "info": { ... }, "lang": "<iso639-1>", "awaitFrom": "owner" | "contact" | "any"}

- say=prose, next="listen"  — reply and stay open (ask, or propose-and-wait).
- say=null,  next="listen"  — DELIBERATE SILENCE, stay open. Chatter that is not for you. This is
                              REAL and load-bearing: you are listening to a real conversation
                              between Marcelo and another person, and you must NOT interject
                              into every message. Stay silent, keep the conversation open.
- say=prose OR null, next="execute" — run the skill(s). "say" is optional here and usually null.
- say=prose, next="done"    — reply and close ("okay, forget it", or a plain answer with nothing

- say=null,  next="done"    — close silently. This is the ORDINARY end of a successful execute:
                              the skill already sent its own outcome message, so anything you add

- say=null,  next="answer"  — answer his question directly with the native toolset. "say" is NOT

- "skills": ONLY when next="execute". A list of task ids (in run order), using ONLY ids from the

- "info": ONLY when next="execute". The declared inputs of the FIRST skill in "skills", filled

- "awaitFrom": ONLY meaningful when next="listen". WHO the next message should come from —

## READING BACK A SKILL'S RESULT
After you EXECUTE a skill that returns a value, you get one more turn: the RESULT it returned and
the prose it already sent to him (YOU ALREADY SAID). Read the result and decide what is left —
usually nothing, so reply {"say": null, "next": "done"}. You may "say" or "listen" if there is
genuinely more to do. You may NOT "execute" on a read-back turn: a new action needs a new message
from him first. If the skill already told him the outcome, do not repeat it — close.

Routing rules:
- You will be told whether there is a quoted (replied-to) audio in the message; use that to disambiguate.
- If the message is a REPLY to a message that contains a Google Calendar link, it
  is almost certainly a calendar action (edit or delete/cancel) — including a bare
  "yes"/"confirm" reply confirming a cancellation. Route it to the calendar task.
- COMPLAINTS ARE NOT COMMANDS. If Marcelo is telling you that you ALREADY DID something
  wrong — past tense, blaming the secretary ("you made a mistake", "that's wrong", "you got
  the time wrong", "você errou") — route it to the FEEDBACK task, **even when the subject is
  a calendar event or a task**. The subject matter is not the intent: "you scheduled that at
  the wrong time" is a BUG REPORT, not a request to schedule anything. Filing it as feedback
  is how the secretary learns; executing it as a fresh order is a second mistake on top of
  the first.
- He can want BOTH — to report the mistake AND to have it fixed now ("you got the time
  wrong, move it to 5pm"). Then execute BOTH skills, feedback first:
  {"next": "execute", "skills": ["feedback", "calendar_action"], ...}.

============ EXTRACTION RULES for "calendar_action" (that skill's own rulebook) ==========
Choosing "action":
- "create": User wants to schedule/create a NEW meeting or event.
- "delete": User wants to cancel/delete/remove an EXISTING event. This
  almost always happens when the order is a REPLY to a message that contains a
  Google Calendar link. If the quoted message has a calendar link and the order
  asks to cancel/delete/remove — or is just an affirmative like "yes"/"confirm"
  right after a cancellation was proposed — choose "delete".
- "edit": User wants to CHANGE an EXISTING event — reschedule it (move to
  another time/date), change its length/duration, add or remove an attendee, or
  rename it. Like delete, this is almost always a REPLY to a message that contains a
  Google Calendar link, but the order asks to move/change/reschedule/rename/add/remove
  rather than call the whole event off. Choose "edit" (NOT "delete") whenever the event
  survives with a modification; choose "delete" only when the event is cancelled entirely.
- "list": User is ASKING what's on the calendar — a READ-ONLY query about
  existing events (e.g. "what's on my calendar tomorrow?", "do I have anything Friday
  afternoon?", "what's my next meeting?"). Nothing is created, changed, or cancelled.

The router — route()

Called once per turn (server.js:685). It does three things in one Claude call: decide the next state, pick the skill(s) and extract the first skill's declared inputs, and detect language. Context in: owner, labelled transcript, now-time, contact, quoted info, the skill catalog, tags, and media blocks. Model: ctx.model (or media.model for file turns), max_tokens:1024.

The reply contract (prompt-only)

{"say": "<prose>" | null,
 "next": "listen" | "execute" | "done" | "answer",
 "skills": ["<skill id>", ...],      // execute only, ids from the catalog
 "info": { ... },                     // execute only — the FIRST skill's declared inputs
 "lang": "<iso639-1>",
 "awaitFrom": "owner" | "contact" | "any"}

Rules the prompt enforces: info fields that can't be found must be null ("a null is ALWAYS better than a guess"); lang is locked to the conversation's first message; before anything is written to the world the owner must have agreed. The skill catalog is injected via describeInputs() — each skill's description, opaque field declarations, and rulebook().

⚠ Top structural brittleness
The router call carries no output_config — the JSON shape is demanded in the prompt text only. parseJsonReply (a balanced-brace scanner) is therefore on the critical path: ~4% of replies leak prose before the JSON and are recovered by it; anything it can't recover silently becomes degraded → "I didn't understand" (router/router.js:9-11, 176-177). There is also no SDK timeout on the classification call (only the answer pass is bounded), and a truncation-caused degrade is indistinguishable from a refusal in the logs.

answer() & native tools

Only when route() returns next:"answer". Runs a tool-enabled Claude call (max_tokens:2048) with web_search / web_fetch (and optional code_execution) from nativeTools.js — gated by the NATIVE_TOOLS switch. Caps: NATIVE_ANSWER_TIMEOUT_MS=30000, NATIVE_MAX_TOOL_HOPS=4, and a per-conversation NATIVE_MAX_ANSWERS=6. It never throws — returns {text, lang, hops, outcome} with outcome ∈ ok | timeout | tool_error | refusal.

How Claude is actually called (llm.js)

  • Thinking is disabled globally — withThinkingDefault wraps ctx.anthropic once at boot and injects thinking:{type:"disabled"} unless the caller set it. This is why max_tokens:1024 is safe on the router.
  • Model comes from callers (no hard-coded ids). Defaults: CLAUDE_MODEL/VISION_MODEL = claude-sonnet-5; TRANSLATE_MODEL = claude-haiku-4-5-20251001.
  • No temperature set. Skills that DO call the model use jsonFormat(schema) → output_config — the router deliberately does not.

Infra · Confirmation (confirm.js)

The shared yes/no/unrelated classifier. In the converted @mary flow the orchestrator's model handles confirmation directly, but this remains the reusable primitive. classifyConfirmation(ctx,{action}) judges only the latest message against a pending action and returns confirm | decline | unrelated. The safe default is unrelated — any doubt, refusal to parse, or API error returns unrelated (a no-op), so a confirmation error can never trigger an irreversible write.

Infra · Self-learning / failure capture (selflearning.js)

This is the system that turns every failure into a Markdown report on disk (later synced to the Mac and turned into a bugfix plan). A high volume of reports here is the direct signal that the flow is failing often.

  • Five triggers: machine — throw:router, throw:skill, unrouted, soft (any ctx.sendFailure); human — reported (the feedback skill).
  • Two invariants: it never throws, and it never silently drops an owner-reported note.
  • One report per turn (ctx._turn.captured guard). Machine failures dedupe within a 10-min window and cap at 20/hour; owner reports never dedupe and cap at 10/hour (a pure disk backstop).
  • Reports are redacted (they land in a git repo) and carry the order, the symptom, a stack, an auto-analysis guess, recent logs, and the transcript.
